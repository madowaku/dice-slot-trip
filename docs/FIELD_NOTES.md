# DICE SLOT TRIP — FIELD NOTES

> 開発中に得られた「再利用できる知見」を蓄積するノート。
> これは仕様書ではなく、実装時の判断原則・失敗回避・プレイテスト知見をCodexや将来の自分へ渡すための外部記憶。

## Codex向け運用ルール

1. 作業開始時にこのファイルを読む。
2. FIELD NOTEと矛盾する変更を行う場合は、その理由を明示する。
3. 一時的な仕様値は仕様書へ、再利用できる判断原則だけをここへ残す。
4. 新しいプレイテストで既存NOTEが否定された場合は削除せず、`SUPERSEDED` を付けて後続NOTEへ繋ぐ。
5. 実装完了時、新しい再利用可能な知見が得られた場合のみNOTE追加候補を報告する。

# A. CORE GAME FEEL

## FN-001 — サイコロは「結果」より「振った感」を優先する
**Status:** ACTIVE  
複雑なうねりや過剰演出より、自然な回転と停止の方が「自分で振った」感覚が強い。タイミングを狙えるゲームでは、入力と視覚結果の因果を崩さない。

## FN-002 — 出目を見る瞬間に判断が始まる設計が強い
**Status:** ACTIVE  
サイコロを振ったあと、ただ結果を見るだけでは弱い。出目を見た瞬間に「どちらへ行くか」「避けられるか」「何を捨てるか」を考えさせる。

## FN-003 — 運だけでも、完全情報だけでも弱い
**Status:** ACTIVE  
面白さは「出目の運」と「その後の読み」の混合にある。何も考えず勝てる状態も、運がほぼ意味を持たない状態も避ける。

## FN-004 — 1周目からゲームの本質を出す
**Status:** ACTIVE  
重要な障害・判断・駆け引きを高周回まで隠さない。1周目は易しくてよいが、「何を読むゲームか」は最初から体験させる。

## FN-005 — 周回強化は「慣れた頃に一段上がる」
**Status:** ACTIVE  
難易度上昇は毎周ではなく、数周ごとに一段階上げる方が学習と達成感を作りやすい。長く周回するプレイヤーも想定する。

# B. MAP / BOARD DESIGN

## FN-006 — マス種類は覚えられる数に抑える
**Status:** ACTIVE  
マス効果を増やしすぎると、プレイヤーは効果を記憶せずアイコンを無視し始める。種類を増やすより、既存マスの配置と組み合わせで変化を作る。

## FN-007 — アイコンは意味を直接伝える
**Status:** ACTIVE  
RESTのような回復マスは、文字よりハートなど意味が即座に分かる記号を優先する。凡例を読ませる前提にしない。

## FN-008 — 危険マスは一目で危険だと分からせる
**Status:** ACTIVE  
RISKのように直感的に理解されるマスは強い。危険マスは色・形・記号・演出を一貫させる。

## FN-009 — 近道は「得」だけでなく緊張を作る
**Status:** ACTIVE  
近道は距離短縮だけでは判断にならない。RISKとRESTの交互配置など、進む価値と怖さを同時に置く。

## FN-010 — 分岐は数字で優劣を説明できる形にする
**Status:** ACTIVE  
「本線9マス vs 近道5マス」のように、選択価値を定量で確認できる方が調整しやすい。

## FN-011 — 長いマップでも現在位置の理解を失わせない
**Status:** ACTIVE  
90～120マス級では、全体の長さより「今どこか」が重要。進捗表示、現在マス、次の目標を常に見える状態にする。

## FN-012 — 収集物は“狙える”必要がある
**Status:** ACTIVE  
御朱印のような収集要素は、ぴったり停止要求が厳しすぎると収集欲より諦めが勝つ。出現数、再挑戦機会、補助効果のいずれかで狙いやすさを確保する。

## FN-013 — EVENTは前半に詰め込みすぎない
**Status:** ACTIVE  
序盤は基本ルールの理解を優先する。EVENTなど追加判断は、移動ルールに慣れた後半へ寄せてもよい。

## FN-014 — 同じマスでも配置文脈で意味が変わる
**Status:** ACTIVE  
REST単体では単純でも、RISK直後や近道上では判断要素になる。新マス追加より配置設計を先に検討する。

# C. HP / LIFE / ITEM / ECONOMY

## FN-015 — HPとLIFEは役割を分ける
**Status:** ACTIVE  
HPは「現在の耐久」、LIFEは「復活可能回数」。同じハート系UIで混同させない。

## FN-016 — LIFEは残機だと明示する
**Status:** ACTIVE  
LIFE表示は猫アイコン＋「あと ×3」など、回復ゲージではなく残機だと直感的に伝える。

## FN-017 — 即死感より“まだ続けられる”感を作る
**Status:** ACTIVE  
RISK数回で即終了すると周回ゲームとして心理的に重い。HP消耗とLIFE消費を分け、失敗しても旅を続けられる余地を作る。

## FN-018 — 満タン報酬にも達成演出を残す
**Status:** ACTIVE  
10周ボーナスなどでLIFEが上限でも、何も起きないように見せない。報酬不能でも「達成した」というスタンプや演出は返す。

## FN-019 — アイテムは説明より効果を短くする
**Status:** ACTIVE  
「HP+1」「次の出目+1」「次のRISK無効」程度の一文で理解できる効果を優先する。条件分岐が長いアイテムは避ける。

## FN-020 — コインは長期動機に繋げる
**Status:** ACTIVE  
その場だけの点数ではなく、累積して後のステージやカジノで使えるようにすると周回理由が生まれる。

## FN-021 — スコアの加算根拠を隠さない
**Status:** ACTIVE  
「なぜ増えたか分からないスコア」は意味を失う。1マス=1点など、説明不要なほど単純な加算ルールを優先する。

---

# D. BOSS / MINI-GAME DESIGN

## FN-022 — ボス戦は5～8回のサイコロで終わる密度を目指す
**Status:** ACTIVE  
短時間でも判断が連続する方がよい。長さより1回ごとの意味を濃くする。

## FN-023 — “無被弾で簡単に終わる”は危険信号
**Status:** ACTIVE  
障害が出ていても、実際には全部避けられるなら難易度は成立していない。クリア率だけでなく「危ないと思った瞬間」があるかを見る。

## FN-024 — 小さい出目にも役割を持たせる
**Status:** ACTIVE  
終盤で空きマスが減る、狭い隙間を通るなど、小さい出目が小回りとして強くなる状況を作る。大きい出目が常に得になる設計を避ける。

## FN-025 — 先読みできる障害は面白い
**Status:** ACTIVE  
完全ランダム障害より、「次に狐火がここへ来る」「丸太が流れてくる」など未来を少し見せる方が読みが生まれる。

## FN-026 — 移動自由度を上げすぎると回避ゲームが崩れる
**Status:** ACTIVE  
出目ぶんを1歩ずつ自由選択すると障害を全部避けられる。左右どちらかを選び、出目ぶんまとめて移動するなど制約を残す。

## FN-027 — 初期難易度にも代表ギミックを出す
**Status:** ACTIVE  
狐火などボス戦の本質になるギミックはLv1から出す。量・速度・組み合わせを弱くして難易度を下げる。

## FN-028 — 難易度は障害数だけで上げない
**Status:** ACTIVE  
障害数、配置密度、予告時間、可動域、同時発生、回復機会など複数軸で調整する。単純な物量増加だけでは運ゲー化しやすい。

## FN-029 — ボス報酬は次の旅へ繋げる
**Status:** ACTIVE  
勝利後のHP回復ルーレットなど、次の周回を始めたくなる小さな回復・補給を置く。

# E. UI / UX

## FN-030 — 重要情報は常時表示する
**Status:** ACTIVE  
HP、LIFE、COIN、LAP、現在進捗など、判断に使う情報は必要な瞬間だけ出さない。視線移動が少ない位置へ固定する。

## FN-031 — 進捗表示は「1/90」のように具体化する
**Status:** ACTIVE  
抽象的なバーだけでなく、現在地/総マス数を数字でも見せる。長い旅ほど数字が効く。

## FN-032 — 画面を美しくしても操作領域を圧迫しない
**Status:** ACTIVE  
マップを大きく見せすぎてボタン・情報領域が狭くなるなら、見た目の迫力より操作性を優先する。

## FN-033 — ステージごとの個性とUI骨格を分ける
**Status:** ACTIVE  
カイロ・アマゾン・京都で背景や演出は変えてよい。ただしHP/LIFE/COIN/サイコロ操作など共通UIの位置と意味は揺らさない。

## FN-034 — チュートリアルは全文ではなく“次の一手”を教える
**Status:** ACTIVE  
初見プレイヤーに一度に全部説明しない。現在必要な判断だけをカードや短文で伝える。

## FN-035 — 効果説明は実プレイ画面と同じ語彙を使う
**Status:** ACTIVE  
説明画面で「体力」、本編で「HP」など表記を揺らさない。アイコン・名称・数値表現を統一する。

## FN-036 — BGM/SFXはゲーム感を大きく引き上げる
**Status:** ACTIVE  
見た目が同じでも音が入ると完成度の印象が大きく上がる。音は終盤の飾りではなく、早めのプレイテスト対象にする。

# F. PLAYTESTING

## FN-037 — 家族テストは説明なしで見る
**Status:** ACTIVE  
「ここを押して」「これはこういう意味」と説明するとUX問題が隠れる。まず黙って触ってもらい、迷った場所を記録する。

## FN-038 — プレイヤーの言葉より行動を優先する
**Status:** ACTIVE  
「分かった」と言っていても、同じ場所で迷うなら理解していない。発言より操作・停止・戻る・誤タップを見る。

## FN-039 — “簡単だった”より“どこで考えたか”を聞く
**Status:** ACTIVE  
難易度評価だけでは原因が分からない。「どの出目で迷った？」「危ないと思った瞬間は？」を確認する。

## FN-040 — 長時間プレイヤーを基準から外さない
**Status:** ACTIVE  
何十周もするプレイヤーがいるなら、5周までの設計だけで終わらせない。高周回まで破綻しない上昇カーブを考える。

## FN-041 — スクショはUI不具合の有力な証拠
**Status:** ACTIVE  
実機スクリーンショットは、狭さ・視線・重なり・文字サイズの確認に強い。可能なら実装前後で比較する。

## FN-042 — 初見プレイと熟練プレイを分けて評価する
**Status:** ACTIVE  
初見には理解しやすさ、熟練者には判断の深さが必要。片方のテスト結果だけで難易度を決めない。

# G. AI / CODEX WORKFLOW

## FN-043 — 仕様決定と実装を同じAI工程に詰め込まない
**Status:** ACTIVE  
設計判断、実装、テスト、完了判定を一気にやらせると自己正当化が起きやすい。可能なら工程を分ける。

## FN-044 — 大改修前に基準版を固定する
**Status:** ACTIVE  
動作している版をタグやブランチで固定してから変更する。「戻れる場所」があるだけで大胆な改善を安全に試せる。

## FN-045 — 大改修は小さな検証単位へ分割する
**Status:** ACTIVE  
マップ、HP/LIFE、EVENT、UIを一度に触らない。1つずつ変更→検証→次へ進む。

## FN-046 — Codexには“変更禁止領域”も書く
**Status:** ACTIVE  
変更してほしい箇所だけでなく、壊したくない既存挙動も明示する。特にセーブ、サイコロ入力、進行管理、既存ステージ互換は保護対象にしやすい。

## FN-047 — 実装指示書には検証条件を含める
**Status:** ACTIVE  
「実装する」だけでなく、「何を確認すれば完了か」まで書く。例: HP0→LIFE減少→HP回復→継続、など。

## FN-048 — AIに履歴を推理させない
**Status:** ACTIVE  
過去会話を毎回推測させるより、CURRENT_SPECとFIELD_NOTESに決定事項を外出しする。曖昧な記憶より短い一次資料を優先する。

## FN-049 — FIELD NOTEは“失敗の再発防止”を優先する
**Status:** ACTIVE  
ただの成功メモより、「何をしたら使いにくくなったか」を残す方が価値が高い。失敗を消さず、判断ルールに変換する。

## FN-050 — 新しい知見は具体例＋一般原則で残す
**Status:** ACTIVE  
「京都Lv1で狐火を出す」だけでは再利用しにくい。「本質ギミックはLv1から出す」のように一般化して記録する。

# H. RELEASE / VERSIONING

## FN-051 — セーブ互換はビルド前に確認する
**Status:** ACTIVE  
APK更新時に既存記録が消えるかどうかは、パッケージID・保存方式・署名・データ構造変更に依存する。配布前に必ず更新インストールで検証する。

## FN-052 — 実機更新テストは新規インストールと分ける
**Status:** ACTIVE  
「新規インストールで動く」と「旧版から更新して動く」は別テスト。両方をチェックする。

## FN-053 — 完成度より“壊さず改善できる状態”を先に作る
**Status:** ACTIVE  
個人開発では一発完成より、安定版→小改修→確認の反復が強い。安全に改善できるパイプライン自体を資産と考える。

# NOTE TEMPLATE

```md
## FN-XXX — 短い原則名
**Status:** ACTIVE / EXPERIMENTAL / SUPERSEDED / REJECTED

観察した事実・起きた問題。

そこから得られた再利用可能な判断原則。

必要なら具体例・例外・参照先。
```

## Status

- **ACTIVE**: 現在の判断原則として採用
- **EXPERIMENTAL**: 仮説。追加テストが必要
- **SUPERSEDED**: 後続NOTEで置き換え済み
- **REJECTED**: テストで不採用と判断

# MAINTENANCE RULE

このファイルを肥大化させすぎない。

- 一時的な数値設定 → 仕様書へ
- 1ステージだけの座標 → ステージデータへ
- バグの詳細ログ → Issueへ
- 再利用できる判断原則 → FIELD_NOTES.mdへ

判断基準はひとつ。

> **「将来の別ステージ・別ゲーム・別AI作業でも役立つか？」**

役立つならFIELD NOTE候補。
